# PRD 구현 (원장 → 커밋 → 마감)

PRD 하나를 `todo` 에서 닫힌 이슈까지 끌고 간다. 이 스킬을 따르는 것은 팀장(주 세션)이다. 팀원이 구현하고, 러너가 판정하고, 팀장이 검수해 커밋한다 (`CLAUDE.md` "팀"). 작업이 끝났는지는 `pnpm ledger:verify` 의 종료 코드가 정하고, 그 결과를 원장에 쓰는 것도 러너뿐이다.

구현은 PRD 마다 따로 만든 워크트리(브랜치 `prd/<이슈>`)에서 한다. 사용자의 pane 오른쪽에 그 워크트리의 pane 을 열고(herdr 가 없으면 사용자가 새 터미널에서 띄운다), 거기서 도는 Claude 세션이 이 스킬의 나머지를 따른다. 사용자가 대화하던 세션은 다음 PRD 를 쓰거나 다른 일을 계속한다. 마감 때 브랜치를 main 에 fast-forward 로 합쳐 푸시한다. PR 은 쓰지 않는다.

인자는 이슈 번호(`12` 또는 `#12`)나 캐시 경로(`docs/prd/<파일>.md`)다. 러너 명령에는 `#` 없이 번호만 쓴다. 셸에서 `#` 은 주석을 시작한다.

## 0. 어느 세션이 하는가

환경 변수 `HARNESS_IMPL` 을 본다.

```bash
echo "${HARNESS_IMPL:-}"
```

- **비어 있거나 이 이슈가 아니면** 사용자의 세션이다. 구현 pane 을 열어 넘기고 여기서는 멈춘다.

  ```bash
  pnpm wt:pane <이슈>     # 워크트리가 없으면 만들고, 새 탭에 pane 을 열어 Claude 를 띄우고 /implement-prd <이슈> 를 보낸다 (herdr 가 없으면 띄울 명령만 알린다)
  ```

  출력된 pane 과 agent 이름(`impl-<이슈>`)을 사용자에게 알린다. 포커스는 옮기지 않는다. 그 세션이 막히면(`herdr agent get impl-<이슈>` 가 `blocked`) 사용자가 그 pane 으로 가서 답한다. 이 세션은 구현에 손대지 않는다. herdr 가 없어 pane 을 열지 못하면 `wt:pane` 이 알려 준 명령(`cd <워크트리> && HARNESS_IMPL=<이슈> claude '/implement-prd <이슈>'`)을 사용자에게 그대로 전하고 멈춘다. main 에서 구현을 시작하지 않는다.

- **이 이슈면** 구현 세션이다. 아래를 전부 따른다. 작업 디렉터리는 워크트리(`pnpm wt:status` 가 보여 주는 `prd-<이슈>`)이고 브랜치는 `prd/<이슈>` 다.

## 시작하기 전에 확인한다

하나라도 어긋나면 멈추고 무엇이 어긋났는지 말한다.

1. `git branch --show-current` 가 `prd/<이슈>` 다. `main` 이면 워크트리 pane 이 아니다. 0 단계로 돌아간다.
2. PRD 를 읽는다. 캐시(`docs/prd/`)는 본 체크아웃과 링크로 같이 쓴다. 없으면 `pnpm prd:pull <이슈>` 로 받는다. 머리말의 `issue` 가 원장 이름이다.
3. 원장이 있다: `docs/ledger/<이슈>.json`. 없으면 `prd` 스킬의 5단계(`pnpm ledger:new`)가 먼저다. 이 스킬은 원장을 만들지 않는다.
4. `git status --short` 가 비어 있다. 남의 변경이 섞인 채로 시작하지 않는다.
5. 원장의 `depends_on` 에 적힌 이슈가 모두 닫혀 있다.
6. `needs_spec` 작업이 있으면 사용자에게 검증 방법을 묻는다. 지어내지 않는다.
7. PRD 의 `scope_paths` 가 닿는 영역의 `CLAUDE.md` 를 읽는다: `apps/<영역>/` 이면 `apps/<영역>/CLAUDE.md`. 팀장 세션은 그 영역의 파일을 직접 읽지 않으면 이 문서를 받지 못하므로, 검수의 기준으로 삼으려면 여기서 읽어 둔다.

`pnpm ledger:status <이슈>` 가 지금 상태를 보여 준다. PRD 의 `## 병렬 계획` 이 어느 작업을 함께 돌릴지 알려 준다.

## 작업을 단계마다 한꺼번에

`todo` 이고 의존성이 모두 `done` 인 작업을 **전부** 모아 한 단계로 돌린다. 동시에 맡길 수 있는 팀원은 개발 셋과 디자인 하나다. 모인 작업이 그보다 많으면 PRD 의 병렬 계획 순서대로 네 개까지 먼저 하고 나머지는 다음 단계로 넘긴다.

1. **집는다**: 단계의 작업을 모두 `pnpm work <이슈> <작업>` 으로 집는다. `todo → doing` 으로 바뀌고 시작 시각이 찍힌다. 범위와 검증 명령이 출력된다. 이슈의 첫 작업을 집으면 보드의 카드가 In progress 로 옮겨진다.
2. **함께 맡긴다**: 단계의 작업을 **한 메시지에서** 팀원들에게 넘긴다. 서버, DB, 인프라, 도구는 `developer`, 화면은 `designer` 다. 팀원마다 이슈 번호, 작업 ID, 범위, 읽을 조사 보고서, 그리고 같은 단계에서 다른 팀원이 고치고 있는 범위를 알려 준다. 한두 줄 고침과 문서 작업은 팀장이 직접 한다.
   - **명단을 돌린다.** 팀원들을 띄우면 각자의 agent ID 가 돌아온다. 곧바로 팀원마다 `SendMessage` 로 같은 단계의 명단을 보낸다: 작업 ID, agent ID, 범위, 한 줄 역할. 팀원은 이 ID 로 서로에게 직접 묻는다 (`.claude/agents/developer.md` "팀원 간 소통"). 이름으로는 닿지 않고 ID 로만 닿는다. 팀장에게는 `main` 으로 보내 온다.

     ```
     #12 S2 단계 명단. 필요한 것은 ID 로 직접 묻고, PRD 와 어긋나면 main 에 알린다.
     - S2 apps/api/src/orders/   a1b2c3…  (너)
     - S3 apps/web/src/orders/   d4e5f6…  (화면, S2 의 응답 모양을 쓴다)
     - S4 apps/api/src/db/       789abc…  (테이블)
     ```

   - 팀원이 `main` 으로 보낸 물음에는 짧게 답한다. PRD 를 고쳐야 하는 물음이면 단계를 멈추지 말고 그 작업만 돌려보낸 뒤 PRD 와 원장을 고친다.
   - 같은 단계의 작업끼리 범위가 겹치면 PRD 가 틀린 것이다. 함께 돌리지 않고 하나를 다음 단계로 미루고, 마감 보고에 적는다.
   - 팀원은 출력된 범위 안에서만 고친다. 범위 밖 파일은 읽기만 한다.
   - 테스트를 먼저 쓰는 작업(원장의 `tdd` 가 `true`: `project.config.json` 의 `tddAreas` 아래의 제품 코드)은 테스트만 쓴 상태에서 `pnpm ledger:red <이슈> <작업>` 으로 실패를 기록한 뒤 구현한다. 이 기록이 없으면 러너가 판정을 내리지 않는다. 인프라, 도구, 문서는 해당하지 않는다.
   - 공용 타입을 생성하는 단계가 있으면 그 작업은 PRD 가 첫 단계에 홀로 두었어야 한다. 같은 단계에 둘 이상이 생성 명령을 돌리면 생성 파일이 서로 덮인다. 생성된 파일은 손으로 고치지 않는다.
   - 테스트 픽스처는 지어낸 값으로 만든다. 실제 고객 데이터를 넣지 않는다.
   - 범위 밖을 고쳐야 한다면 멈추고 말한다. PRD 의 범위가 틀린 것이므로 PRD 와 원장을 먼저 고친다.
   - 화면을 띄워 확인할 때는 워크트리에서 개발 서버를 띄운다(루트 `CLAUDE.md` "명령"). 본 체크아웃의 서버가 같은 포트에 떠 있으면 사용자에게 알리고 그쪽을 먼저 내린다. 두 체크아웃은 같은 DB 와 `data/` 를 본다.
3. **판정받는다**: 팀원이 각자 `pnpm ledger:verify <이슈> <작업>` 을 돌린다. 통과하면 `done`, 실패하면 횟수가 쌓인다.
   - 3번째 실패부터는 다시 돌리기 전에 원인을 읽는다. 5번 실패하면 `parked` 가 되고 사람이 판단한다.
   - 검증 명령이 작업에 맞지 않는다면 명령을 고치는 것이 답이다. 통과시키려고 테스트를 지우거나 약하게 만들지 않는다.
   - 같은 패키지의 작업이 함께 돌면 한쪽의 미완성 코드 때문에 다른 쪽의 검증이 실패할 수 있다. 실패 출력이 자기 범위 밖의 파일을 가리키면 그 팀원의 작업이 끝난 뒤 다시 돌린다. 이것은 실패 횟수로 세지만 원인을 보고에 적는다.
4. **돌아오는 대로 검수한다**: 팀원이 돌아올 때마다 그 작업의 변경만 `git diff -- <범위>` 로 직접 읽는다. 다른 팀원이 아직 일하고 있어도 기다리지 않는다.
   - 범위 밖을 고치지 않았는가. 같은 단계의 다른 작업 범위를 건드리지 않았는가.
   - 루트 `CLAUDE.md` 의 "지키는 선", "읽지 않는 것", "데이터를 두는 원칙", "출처 경계"와 그 영역의 `CLAUDE.md` 에 맞는가. 계약된 범위를 넘지 않았는가. DB 에 계산한 값이나 쓸지 모르는 칸이 생기지 않았는가. 인프라를 쓴다면 자원이 `infra/` 밖에서 만들어지지 않았는가.
   - `CLAUDE.md` 를 고친 작업이면 루트 `CLAUDE.md` "적는 기준"에 비춰 본다. 규칙과 설계 결정만 남고, 코드의 설명(파일 목록, 칸의 나열, 화면의 설명, 이력)이 들어왔으면 돌려보낸다. 같은 사실이 두 문서에 적히지 않았는가.
   - 테스트나 검증 명령이 약해지지 않았는가. 테스트가 지워지거나 약해졌으면 직접 판정하지 않고 `test-reviewer` 에게 맡긴다. "되살릴 것"이 하나라도 있으면 구현한 팀원에게 돌려보낸다.
   - 테스트를 먼저 쓰는 작업이면 새 동작마다 테스트가 있는가. 실패 기록(`red_at`)이 엉뚱한 실패로 채워지지 않았는가.
   - 보고한 내용과 실제 변경이 일치하는가.
   - 팀원끼리 주고받은 약속(타입 이름, 응답 모양, 칸 이름)이 양쪽 코드에 같은 모양으로 들어갔는가. 보고의 "주고받은 것"을 양쪽 diff 와 맞춰 본다.

   걸리는 것이 있으면 커밋하지 않고 같은 팀원에게 무엇을 고칠지 돌려보낸다. 원장은 이미 `done` 이어도 커밋은 검수를 지난 뒤다.
5. **작업마다 커밋한다**: 검수를 지난 직후, 그 작업의 범위 안 파일과 원장만 한 커밋으로 묶는다. 다른 팀원이 아직 고치는 파일은 `git add` 하지 않는다. 그래서 `git add -A` 를 쓰지 않는다.

   ```bash
   git status --short            # 범위 안의 새 파일(??)이 빠지지 않았는지, 남의 범위가 섞이지 않았는지 본다
   git add <범위의 파일들> docs/ledger/<이슈>.json
   git commit -m "feat(<영역>): <작업 제목> (#<이슈> <작업 id>)"
   ```

   제품 코드면 `feat` 나 `fix`, 그 밖은 `chore` 나 `docs` 다. 원장 파일은 다른 팀원의 판정도 함께 담고 있을 수 있다. 그래도 그대로 커밋한다. 판정은 러너가 쓴 사실이다.

단계의 작업이 모두 `done` 이나 `parked` 가 되면 다음 단계를 모은다. 모든 작업이 끝날 때까지 되풀이한다.

## 마감

1. **전체를 한 번 돌린다**: `pnpm test`(스택의 테스트는 `test:stack` 으로 함께 돈다). 작업별 검증은 그 패키지만 보므로, 패키지 사이가 어긋났는지는 여기서 드러난다. 실패하면 고치고 커밋한 뒤 다시 돌린다.
   - **개발 기록 한 항목을 더한다**: 사용자에게 보이는 변화가 있으면 `showcase/dev-notes.json` 에 `{ date, kind, title, body, issue }` 한 항목을 사용자의 말로 쓴다(ADR-0029). 종류는 `bug` / `feature` / `improvement` 이고, 이 PRD 를 `planned` 로 미리 적어 두었으면 그 항목의 종류와 날짜를 고친다. 코드 이름, 이슈 번호, 금지어를 넣지 않는다(레포 검사가 본다). 사용자에게 보이는 변화가 없으면 생략한다. `pnpm test` 앞에 하고 같이 커밋한다.
2. **PRD 의 `## 사람이 할 일` 을 `qa` 팀원에게 맡긴다**: 항목이 있으면 사용자에게 묻지 않고 `qa` 팀원(`.claude/agents/qa.md`)을 띄워 이슈 번호, 항목의 글 그대로, 확인할 커밋 sha, PRD 의 수용 기준을 준다. 그 팀원은 떠 있는 제품에서 항목을 직접 해 보고 `outputs/qa/<이슈>/report.html` 에 스크린샷, 사유, 결과를 남긴다. `qa.md` 의 "이 프로젝트의 QA 설정"이 아직 `[TODO]` 면 띄우지 않고, 항목을 사용자에게 보여 직접 해 달라고 묻는다. 돌아온 판정을 읽는다.
   - 모두 `통과` 면 다음으로 간다.
   - `실패` 가 있으면 마감하지 않는다. 그 항목이 가리키는 작업을 구현한 팀원에게 돌려보내고, 고친 뒤 `qa` 를 다시 돌린다. PRD 의 기대가 틀린 것이면 PRD 와 이슈 본문을 고치고 다시 돌린다.
   - `확인 불가` 가 있으면 무엇이 정해져야 하는지와 함께 사용자에게 묻고, 답을 받을 때까지 마감하지 않는다.
   - 항목이 없으면 `qa` 를 띄우지 않는다.
3. **`pnpm finish <이슈>`**: 모든 작업이 `done` 이나 `parked` 면 실측을 `docs/ledger/outcomes.jsonl` 에 한 줄 적고 원장을 지운다. 아니면 남은 작업을 나열하고 실패한다. 한 번만 돌린다. 원장이 지워지므로 두 번째는 실패한다.
4. **마감을 커밋한다**: `finish` 가 출력한 명령 중 커밋까지만 쓴다. `git push` 는 쓰지 않는다. 브랜치는 푸시하지 않는다.

   ```bash
   git add -A docs/ledger
   git commit -m "chore(ledger): #<이슈> 마감" -m "Closes #<이슈>"
   ```

5. **main 에 합쳐 푸시한다**:

   ```bash
   pnpm wt:finish <이슈>     # 브랜치를 main 위로 rebase 하고, 본 체크아웃의 main 에 fast-forward 로 합친 뒤 푸시한다 (origin 이 없으면 합치기만 한다)
   ```

   rebase 가 충돌하면(다른 PRD 가 먼저 들어가 `outcomes.jsonl` 이나 같은 파일을 고쳤을 때) 워크트리에서 충돌을 풀고 `git rebase --continue` 한 뒤 다시 돌린다. 본 체크아웃에 커밋하지 않은 변경이 있으면 실패한다. 그 변경은 사용자의 것이므로 건드리지 않고 사용자에게 알린다.

   `Closes #<이슈>` 가 main 에 닿으면 GitHub 이 이슈를 닫고, 보드의 자동화가 카드를 Done 으로 옮긴다.

6. **실측 확인 보고서를 띄운다**: `qa` 가 보고서를 남겼으면 사용자의 기본 브라우저로 연다. 포커스는 옮기지 않는다.

   ```bash
   open outputs/qa/<이슈>/report.html
   ```

`parked` 작업이 있으면 마감 전에 사용자에게 알린다. 그대로 마감할지, 후속 이슈로 넘길지는 사용자가 정한다.

## 끝났는지 확인하고 그대로 보고한다

```bash
git status -sb                                   # 변경 없음
git -C "$(git rev-parse --git-common-dir)/.." status -sb   # 본 체크아웃의 main: origin/main 보다 앞서지 않음
GH_TOKEN=$(gh auth token --user JadenKimDev) gh issue view <이슈> -R JadenKimDev/beside-pet --json state -q .state
```

`git status` 는 `??` 만이 아니라 모든 줄을 읽는다. 수정(`M`) 한 줄이 남아 있어도 끝난 것이 아니다.

- 끝남: "작업 트리 깨끗함, main 푸시됨(`<sha>`), 이슈 `#<n>` 닫힘, 실측 <작업 합계>, 실측 확인 통과 n/n(`outputs/qa/<n>/report.html`). 완료. 워크트리는 `pnpm wt:remove <n>` 으로 치운다."
- 보류: "남은 것: <작업 id 와 상태, 또는 확인받지 못한 항목>. 이슈 `#<n>` 열림."

워크트리와 이 pane 을 치우는 것은 사용자가 정하고 사용자의 세션이 한다(`pnpm wt:remove <이슈>`). 구현 세션은 치우자고 묻지 않는다. 치우기 전에 소스 디렉터리 아래에 git 이 무시하는 파일이 남아 있으면 `wt:remove` 가 목록을 보이고 멈추므로, 옮기거나 지운 뒤 다시 돌린다. 워크트리의 빌드 산출물은 함께 지워진다. 구현 세션은 자기 pane 을 닫지 않는다. 자기가 서 있는 디렉터리가 사라진다.

## 하지 않는 것

- 원장의 `status`, `passes`, `retries`, 시각을 손으로 고치지 않는다. `pnpm work`, `pnpm ledger:verify`, `pnpm finish` 만 쓴다.
- 검증을 통과시키려고 테스트나 검증 명령을 약하게 만들지 않는다.
- 상태를 확인하려고 `pnpm finish` 를 다시 돌리지 않는다. 상태는 `pnpm ledger:status` 로 본다.
- `git push --force`, `--no-verify` 를 쓰지 않는다. `prd/<이슈>` 브랜치를 원격에 푸시하지 않는다.
- main 체크아웃에서 구현하지 않는다. 본 체크아웃의 파일을 고치지 않는다.
- 다른 이슈의 작업을 같이 고치지 않는다. 눈에 띈 문제는 보고하고 새 PRD 로 넘긴다.
