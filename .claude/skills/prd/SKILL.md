# PRD 작성

Beside Pet 의 작업 하나를 한국어 PRD 로 쓰고, 승인받아 GitHub 이슈로 올린 뒤, 그 원장과 워크트리를 만든다. `implement-prd` 가 여기서 만든 것을 읽어 구현한다. 작업은 팀원 여럿이 동시에 하므로, 나란히 돌 수 있게 나누는 것이 이 스킬의 몫이다.

## PRD 가 사는 곳

정본은 `HCN-335/beside-pet` 의 GitHub 이슈다. `docs/prd/` 는 gitignore 된 캐시이고 커밋하지 않는다.

- 작업의 이름은 이슈 번호다. 따로 만든 티켓 번호는 쓰지 않는다.
- 이슈 제목은 머리말의 `title` 그대로다.
- 이슈 본문은 PRD 파일 그대로다. 머리말(frontmatter)까지 포함한다.
- 열린 이슈는 진행 중, 닫힌 이슈는 끝난 작업이다.
- 이슈는 프로젝트 보드(`project.config.json` 의 `boardNumber`)에서 본다. `prd:push` 가 새 이슈를 보드에 올린다. 번호가 없으면 보드는 건너뛴다.

이슈는 이 머신 밖에 저장되고 고객이 볼 수 있다. PRD 에는 `.env` 의 값, 실제 고객 데이터, 루트 `CLAUDE.md` "읽지 않는 것"의 내용을 싣지 않는다. 범위는 계약된 범위 안이어야 하고, 범위 밖으로 보이는 요구는 PRD 에 넣기 전에 사용자에게 묻는다(`/Users/taehokim/freelance/base/docs/playbook/`).

## 1. 형식을 고른다

| 형식 | 언제 | 본문 |
|---|---|---|
| 기능 | 새 동작, 여러 단계의 작업 | 요약 → 사용자 흐름 → 설계 → 서브 티켓 → 수용 기준 |
| 수정 | 버그, 규칙 위반, 작은 고침 | 증상 → 재현 → 원인 → 고칠 방법 → 서브 티켓 |

틀은 `references/template.md` 에 있다.

## 2. 재료를 모은다

- 기능: 무엇을 하는가(한두 문장), 왜 필요한가, 사용자가 겪는 흐름, 닿는 경로, 먼저 닫혀야 할 이슈.
- 수정: 보이는 증상, 재현 방법(어디서, 무엇을 하면, 무엇을 기대했나), 아는 만큼의 원인.

코드를 읽어서 알 수 있는 것은 묻지 않는다. `docs/research/` 에 이미 정한 것이 있으면 다시 정하지 않고 가리킨다.

결정 기록을 먼저 찾는다: `pnpm docs:search "<이 PRD 의 낱말>"` (도구가 없으면 `grep -ril <낱말> docs/adr docs/devlog`). 나온 ADR 이 있으면 읽고 설계 절에서 가리키며, 그 결정에 어긋나는 설계를 쓰지 않는다. 이 PRD 가 그 결정을 뒤집거나 PRD 로 정리되지 않는 새 결정(외부 서비스, 라이선스, 데이터를 두는 곳, 구조의 경계)을 만들면 새 ADR 을 쓰는 작업을 서브 티켓에 둔다(형식은 `docs/adr/README.md`). 전부 읽지 않는다.

PRD 가 닿는 영역의 `CLAUDE.md` 를 먼저 읽는다(영역마다 `apps/<영역>/CLAUDE.md`). 하위 디렉터리의 `CLAUDE.md` 는 그 디렉터리의 파일을 읽은 세션에만 들어오므로, PRD 를 쓰는 팀장 세션에는 자동으로 들어오지 않는다. 거기 적힌 규칙과 설계 결정에 어긋나는 설계를 쓰지 않는다.

범용화되지 않은 기술(문서가 한 곳에 정리돼 있지 않은 외부 API, 고객의 기존 시스템과의 연동 등)에 기대는 기능이면 초안을 쓰기 전에 `researcher` 에게 조사를 맡긴다. 보고서의 "계획 순서"를 따라 신뢰도 등급이 높은 조각부터 PRD 로 나누고, 설계 절에서 보고서를 가리킨다. 등급 C, D 에 기대는 조각은 실측 작업을 앞에 두거나 다음 PRD 로 미룬다. 새 화면이 있으면 `designer` 에게 화면 안을 먼저 받는다. 잘 알려진 문제는 조사 없이 바로 쓴다.

## 3. 초안을 쓰고, 승인받아 이슈로 올린다

초안은 `docs/prd/<kebab-설명>.md` 에 쓴다. 머리말에 `issue` 와 `file` 은 적지 않는다. 이슈를 만들 때 도구가 채운다.

초안 파일을 쓴 직후 사용자 옆 화면에 연다. 사용자가 따로 말하지 않았다면 늘 이렇게 한다.

```bash
pnpm prd:pane docs/prd/<파일>.md    # herdr 오른쪽 pane 에 vi 로 연다
```

- "열지 마", "대화로만 보여 줘" 같은 지시가 있으면 열지 않는다.
- herdr 가 없어 실패하면 그 사실을 말하고 초안을 대화에 그대로 보여 준다.
- pane 은 한 번만 연다. 초안을 고친 뒤에는 다시 열지 않고, vi 에서 `:e` 로 다시 읽으라고 알린다.
- 사용자가 vi 에서 직접 고쳤을 수 있다. 초안을 더 고치거나 올리기 전에 파일을 다시 읽고, 사용자의 수정을 덮어쓰지 않는다.
- 대화에는 초안 전체를 다시 붙이지 않고, 무엇을 하는 PRD 인지와 사용자가 정해 줘야 할 것만 짧게 적는다.

### PRD 하나의 크기

혼자 main 에 들어가도 레포가 온전한 가장 작은 변경이 PRD 하나다. 같은 영역이라는 이유만으로 무관한 고침을 묶지 않는다. 순서만 있는 관계("A 다음에 B")는 묶지 않고 머리말 `depends_on` 에 적는다.

### 작업은 병렬로 돌 수 있게 나눈다

구현은 개발 팀원 셋과 디자인 팀원 하나가 동시에 한다 (`CLAUDE.md` "팀"). `implement-prd` 는 의존성이 풀린 `todo` 작업을 한꺼번에 집어 함께 맡기므로, 서브 티켓은 같은 시점에 돌 수 있는 작업이 많도록 나눈다.

- **범위가 겹치지 않게 나눈다.** 동시에 돌 작업끼리는 같은 파일을 고치지 않는다. 같은 파일을 고쳐야 하는 일은 한 작업으로 묶거나 의존성으로 순서를 준다. 같은 파일이라도 한쪽이 읽기만 하면 겹치지 않는다.
- **의존성은 진짜로 필요한 것만 적는다.** "먼저 하는 게 자연스럽다"는 의존성이 아니다. 뒤 작업이 앞 작업의 코드(타입, 함수, 테이블)를 쓸 때만 적는다.
- **경계를 먼저 떼어 낸다.** 여러 작업이 함께 쓰는 것(API 타입, DB 마이그레이션, 공용 함수의 시그니처)은 작은 첫 작업(S1)으로 떼고, 나머지가 그 위에서 나란히 돌게 한다. 타입을 생성하는 단계가 있으면 그것도 첫 작업에서 끝낸다.
- **화면과 서버는 나란히 돈다.** 화면 작업은 서버가 줄 데이터 모양만 정해지면 서버 구현을 기다리지 않는다. 데이터 모양을 정하는 작업을 앞에 두고, 화면 작업은 그것에만 의존한다.
- **한 작업은 팀원 하나가 한 번에 끝낼 크기다.** 한 작업이 너무 크면 다른 셋이 논다. 실측(`pnpm ledger:outcomes`)에서 작업 하나가 두 시간을 넘긴 적이 있으면 더 쪼갠다.

본문의 `## 병렬 계획` 에 어느 작업이 함께 도는지 단계별로 적는다. 한 단계에 네 작업(개발 셋과 디자인 하나)까지 두고, 그 이상이면 다음 단계로 넘긴다. 어쩔 수 없이 한 줄로 늘어선 사슬이 있으면 그 이유를 한 줄 적는다.

```markdown
## 병렬 계획

| 단계 | 함께 도는 작업 | 기다리는 것 |
|---|---|---|
| 1 | S1 | - |
| 2 | S2, S3, S4 | S1 의 타입 |
| 3 | S5 | S2, S3 |
```

### 서브 티켓 표

원장은 이 표에서 만들어진다. 열은 머리글 이름으로 찾으므로 순서는 자유다.

| 열 | 필수 | 쓰임 |
|---|---|---|
| `ID` | 예 | 작업 id. 이 PRD 안에서만 통하는 짧은 이름이다: `S1`, `S2` |
| `제목` | 예 | 작업 이름 |
| `범위` | 예 | 이 작업이 고치는 경로. 백틱으로 감싼다. 머리말 `scope_paths` 안에 있어야 한다 |
| `의존성` | 아니오 | `-` 는 없음, 아니면 같은 표의 작업 id |
| `검증` | 아니오 | 백틱으로 감싼 셸 명령. 비우면 범위에서 끌어낸다 |
| `TDD` | 아니오 | `예` 나 `아니오`. 비우면 범위에서 정한다: `project.config.json` 의 `tddAreas`(기본 `apps/`) 아래면 `예`, 나머지(인프라, 도구, 문서)는 `아니오` |

검증 명령은 범위가 속한 패키지에서 나온다.

| 범위 | 끌어내는 명령 |
|---|---|
| `package.json` 이 있는 패키지 (`apps/*`, `packages/*`, `dev-tools`) | `pnpm -F <패키지> typecheck`, `test` 스크립트가 있으면 그것도 |
| 이 작업이 새로 만들 패키지 | `pnpm test` |
| 패키지 밖 (`docs/`, `.claude/`, 루트 파일) | 없음 → `needs_spec` |

pnpm 패키지가 아닌 스택(다른 언어의 서버 등)은 `검증` 칸에 그 스택의 테스트 명령을 직접 적는다.

표의 작업은 명령으로 판정할 수 있는 코딩 작업만이다. 외부 계정 만들기, 고객에게 확인받기, 눈으로 보는 화면 확인은 작업이 아니다. 이런 것은 본문의 `## 사람이 할 일` 에 순서대로 적고, 각 단계에서 무엇을 하고 무엇이 보여야 통과인지 쓴다. 이 항목은 마감 때 사람이 아니라 `qa` 팀원이 떠 있는 제품에서 대신 해 보고 보고서로 남기므로(`implement-prd` 마감), 사람의 감이 아니라 화면, 응답, DB 에서 관찰할 수 있는 기대로 적는다. "예쁜지 본다"가 아니라 "주문 카드에 상태 이름과 금액이 보인다"다. 문서만 고치는 작업은 `검증` 칸에 확인할 수 있는 명령(`test -f docs/...`, `grep -q ... 파일`)을 적는다.

### `CLAUDE.md` 를 고치는 작업

CLAUDE.md 를 고치는 작업은 기본으로 넣지 않는다. 지난 PRD 들이 관행처럼 붙인 "`CLAUDE.md` 갱신" 작업은 코드의 설명을 쌓았고, 루트 `CLAUDE.md` "적는 기준"이 그것을 금한다.

- **넣는 때**: 이 PRD 가 에이전트가 지켜야 하는 새 규칙이나 코드만 봐서는 알 수 없는 설계 결정을 만들었을 때, 또는 이미 적힌 문장을 틀리게 만들었을 때(옮긴 경로, 바뀐 결정)만이다. 새 파일, 테이블, 칸, 환경 변수, 화면이 생긴 것은 이유가 되지 않는다.
- **고치는 곳**: 그 규칙이 닿는 자리다. 한 영역의 것은 그 영역의 `apps/<영역>/CLAUDE.md`, 여러 영역에 걸치거나 파일을 건드리기 전에 알아야 하는 것(지키는 선, 읽지 않는 것, 팀, 작업 흐름)만 루트 `CLAUDE.md` 다. 같은 사실은 한 곳에만 둔다.
- **서브 티켓의 제목**: 무엇을 적는지 쓴다. "서버 영역의 `CLAUDE.md` 에 주문은 지우지 않고 취소 상태로 둔다는 결정을 적는다" 처럼. "`CLAUDE.md`" 한 낱말로 두지 않는다. 범위에는 그 문서 하나만 적는다.
- **검증**: 새 낱말의 `grep` 이 아니라 `pnpm -F @beside-pet/dev-tools test` 다. 문서가 가리키는 경로가 실제로 있는지 검사한다. 더해야만 통과하는 검증은 쓰지 않는다.
- **검수**: `implement-prd` 에서 팀장이 "적는 기준"에 비춰 본다. 코드의 설명(파일 목록, 칸의 나열, 화면의 설명, 이력)이 들어왔으면 돌려보낸다.

### 올리기

사용자가 초안을 승인하면 올린다. 승인 전에는 올리지 않는다.
올리면 파일 이름이 `<이슈 번호>-<이름>.md` 로 바뀐다. 열어 둔 vi 는 옛 이름을 보고 있으므로 닫으라고 알린다.

```bash
pnpm prd:push docs/prd/<파일>.md     # 이슈가 없으면 만들고, 있으면 본문을 갱신한다
```

새 이슈를 만들면 도구가 세 가지를 한다. 머리말에 `issue: <번호>` 와 `file:` 을 적고, 캐시 파일 이름 앞에 번호를 붙이고(`docs/prd/<번호>-<kebab-설명>.md`), 이슈를 보드의 Backlog 에 올린다. 이후 명령에는 출력된 새 경로를 쓴다.

보드에 올리지 못했다는 경고가 나오면 그 이유를 사용자에게 그대로 전한다. 이슈와 원장은 그대로 유효하다.

나중에 고칠 때도 캐시 파일을 고치고 같은 명령을 쓴다. GitHub 에서 직접 고쳤다면 `pnpm prd:pull <이슈>` 로 받아 온다.

## 4. 걸릴 시간을 실측에서 추정한다

```bash
pnpm ledger:outcomes        # 끝난 이슈의 작업별 실측 시간과 범위
```

같은 영역이나 같은 종류의 작업을 기준으로 삼아 `## 추정` 에 낙관, 현실, 비관 세 값을 적는다. 기준으로 삼은 이슈와 표본 수를 함께 적는다. 표본이 없으면 "실측 표본 없음, 감으로 잡은 값" 이라고 쓴다. 근거보다 자신 있게 쓰지 않는다.

## 5. 원장을 만든다

```bash
pnpm ledger:new docs/prd/<파일>.md
git add docs/ledger/<이슈>.json
git commit -m "chore(ledger): #<이슈> 원장"
```

`docs/ledger/<이슈>.json` 이 생긴다. 이슈로 올리기 전의 초안으로는 만들 수 없다. 표가 틀리면 어디가 틀렸는지 말하며 멈추므로 PRD 를 고치고 다시 돌린다. PRD 를 고친 뒤에는 `--force` 로 다시 만든다(작업을 시작하기 전까지만).

만들어진 원장에서 고쳐도 되는 것은 작업의 정의(`title`, `scope`, `verify`)다. 판정 칸(`status`, `passes`, `retries`, 시각)은 러너만 쓴다. `needs_spec` 작업은 `verify` 를 채우고 `status` 를 `todo` 로 바꾸면 풀린다. 이것만 예외다.

## 6. 워크트리를 만든다

원장을 커밋한 직후, 이 PRD 가 일할 워크트리를 만든다. 구현은 main 이 아니라 여기서 한다 (`CLAUDE.md` "작업 흐름").

```bash
pnpm wt:create <이슈>     # prd/<이슈> 브랜치를 main 에서 따고 워크트리에 체크아웃한다. herdr 가 있으면 workspace 로 연다
```

- 원장 커밋이 main 에 있어야 워크트리가 원장을 본다. 커밋 전에 만들지 않는다.
- gitignore 된 로컬 폴더(`data/`, `outputs/`, `docs/prd/`, `docs/research/`, `.env`)는 본 체크아웃의 것을 링크로 같이 쓴다. 워크트리에서도 같은 DB, 같은 PRD 캐시를 본다. 빌드 폴더는 워크트리마다 따로다.
- 포커스는 옮기지 않는다. 사용자에게 워크트리(와 herdr workspace)가 열렸다고만 알린다.
- 워크트리를 만들지 못하면 그 사실을 말하고 멈춘다. main 에서 구현을 시작하지 않는다.

구현을 바로 시작하려면 `implement-prd` 스킬을 따른다. 그 스킬이 구현 세션을 연다(herdr 가 없으면 띄울 명령을 사용자에게 알린다).

## 끝났는지 확인

- [ ] 머리말에 `type: prd`, `title`, `scope_paths` 가 있다
- [ ] 이 PRD 만 main 에 들어가도 레포가 온전하다
- [ ] 서브 티켓의 모든 행은 명령으로 판정할 수 있다
- [ ] 동시에 도는 작업끼리 범위가 겹치지 않고, `## 병렬 계획` 이 있다
- [ ] 계약된 범위 안이고, `.env` 의 값과 실제 고객 데이터가 들어 있지 않다
- [ ] 사용자가 승인했고, 이슈가 있으며 보드에 올라가 있다(못 올렸으면 이유를 전했다)
- [ ] 원장이 있고 커밋됐으며, `needs_spec` 이 있으면 사용자에게 알렸다
- [ ] 워크트리 `prd/<이슈>` 가 있다 (`pnpm wt:status`)
