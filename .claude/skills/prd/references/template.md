# PRD 틀

초안은 `pnpm prd:new <kebab-설명>` (수정 틀은 `--fix`) 이 아래 틀을 복사해 만든다. `issue`, `file` 과 시각(`drafted_at`, `submitted_at`, `approved_at`)은 손으로 적지 않는다. `prd:new` 가 `drafted_at` 을, `pnpm prd:push --draft` 가 초안 이슈를 만들며 머리말 첫 줄에 `issue` 와 `submitted_at` 을, 승인 푸시가 `approved_at` 을 채운다. `depends_on` 에는 먼저 닫혀야 할 이슈 번호를 적는다.

## 기능

```markdown
---
type: prd
title: 한 줄 제목
depends_on: []
scope_paths:
  - apps/api
---

## 요약

무엇을 하고 왜 필요한지 두세 문장.

## 사용자 흐름

1. 사용자가 무엇을 한다.
2. 무엇이 보인다.

## 설계

- 어느 경로에 무엇이 생기는가.
- 지켜야 할 규칙. 루트 `CLAUDE.md` "지키는 선"이나 "읽지 않는 것"에 닿으면 어느 줄인지 적고, 영역의 `CLAUDE.md`(`apps/<영역>/CLAUDE.md`)의 설계 결정에 닿으면 그것도 적는다.
- 이 PRD 가 새 규칙이나 설계 결정을 만들면 적을 자리(`apps/<영역>/CLAUDE.md` 등)를 적고 그 작업을 서브 티켓에 둔다. 아니면 `CLAUDE.md` 작업은 두지 않는다.
- 이미 정해진 것은 `docs/research/` 의 해당 절을 가리킨다.

## 서브 티켓

| ID | 제목 | 범위 | 의존성 | 검증 |
|---|---|---|---|---|
| S1 | 작업 이름 | `apps/api/src/orders/state.ts` | - | |
| S2 | 작업 이름 | `apps/api/src/orders/rules.ts` | S1 | |
| S3 | 작업 이름 | `apps/web/src/orders/` | S1 | |

## 병렬 계획

같은 단계의 작업은 범위가 겹치지 않아 동시에 돈다. 한 단계에 개발 셋 + 디자인 하나까지.

| 단계 | 함께 도는 작업 | 기다리는 것 |
|---|---|---|
| 1 | S1 | - |
| 2 | S2, S3 | S1 의 타입 |

## 수용 기준

- 관찰할 수 있는 결과로 적는다. "결제가 끝나지 않은 주문은 배송 상태로 넘어가지 않는다."

## 사람이 할 일

명령으로 판정할 수 없는 확인이 있을 때만 둔다. 마감 때 `qa` 팀원이 QA 계정으로 대신 해 보므로, 무엇을 하고 무엇이 보여야 통과인지 관찰할 수 있게 적는다.

1. 무엇을 하고, 무엇이 보이면 통과인가.

## 추정

| 구분 | 값 | 근거 |
|---|---|---|
| 낙관 | 작업 N분, 전체 M분, 작성 K분 | 기준 이슈 중 가장 짧은 실측 |
| 현실 | 작업 N분, 전체 M분, 작성 K분 | 기준 이슈와 표본 수(`pnpm ledger:outcomes`), 실측 작업 합계의 중앙값. 작성은 `pnpm ledger:accuracy` 의 작성 구간 중앙값 |
| 비관 | 작업 N분, 전체 M분, 작성 K분 | 기준 이슈 중 가장 긴 실측의 두 배 |
```

2. 기대한 것과 실제로 일어난 것.

## 원인

아는 만큼. 모르면 모른다고 쓰고 조사할 곳을 적는다.
