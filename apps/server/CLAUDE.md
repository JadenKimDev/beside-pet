# apps/server

Rust(axum, sqlx) 서버다. 옛 TS(NestJS) API(2026-10-16 삭제, ADR-0019)의 엔드포인트 겉을 그대로 가진다(ADR-0015). 겉(경로, 요청·응답 모양, 상태 코드, 오류 문구, 환경 변수 이름)은 바꾸지 않는다. 기능의 속은 PRD 마다 포팅과 재설계 중에 고르고 ADR 로 남긴다.

## 가르기

단일 책임과 디커플링은 반드시 지킨다. 크기 상한은 규칙이 아니다.

1. 기능마다 디렉터리 하나(`identity`, `support`, `safety`, `llm`, `metrics`, `shared`). 기능이 커지면 하위 기능 디렉터리로 가른다. 깊이는 책임을 따라가고 숫자로 정하지 않는다.
2. 모듈(파일) 하나는 바뀌는 이유가 하나다. 머리의 `//!` 첫 줄이 그 책임이고, "그리고"가 들어가면 나눈다. 디렉터리의 `mod.rs` 는 그 디렉터리가 맡는 것과 맡지 않는 것을 두세 줄로 적되 파일 목록은 적지 않는다.
3. 기능 안은 책임의 종류로 가른다. 규칙(순수 함수, I/O 없음)·저장(`store`, 그 기능의 테이블의 SQL)·API(`api`, 핸들러와 요청·응답 타입)·흐름(둘 이상을 엮는 것). 흐름이 바깥(DB, 모델, 시계)을 쓸 때는 trait 로 받는다.
4. 다른 기능이 쓸 수 있는 것은 그 기능 `mod.rs` 의 `pub` 뿐이다. `crate::<기능>::<내부 모듈>::…` 경로를 그 기능 밖에서 `use` 하지 않는다. 하위 기능도 같다. 기능 사이의 방향은 `support → identity`, `support → safety`, `support → llm`, `safety → llm`(위기 판정이 모델에 YES/NO 를 묻는다), `metrics → identity`(관리자 가드) 이고, 모든 기능은 `shared` 를 쓸 수 있다. 거꾸로는 쓰지 않는다. 내부 경로는 `pnpm test` 의 레포 검사가 실패로 잡는다.
5. 기능이 바깥(계정 확인, 모델, 대화 저장)을 쓸 때는 trait 로 묻고 `app.rs` 가 구현을 끼운다. 아직 구현이 없는 trait 는 `Unimplemented` 구조체가 `501 Not implemented` 를 낸다. 핸들러에 가짜 동작(메모리 저장, 고정 응답)을 넣지 않는다.
6. 모듈 파일은 `x.rs` 이고 하위 모듈과 테스트는 `x/` 에 둔다. 기능과 하위 기능의 뿌리만 `mod.rs` 다. 테스트는 곁 파일(`x/tests.rs`, `x/tests/<뜻>.rs`)이다. 레포 검사가 `mod.rs` 의 자리를 실패로 잡는다.
7. 같은 일을 하는 함수를 이름만 바꿔 다시 만들지 않는다. 있는 것을 쓰거나 옮긴다. 레포 검사가 같은 몸체를 경고한다.
8. 범용 타입을 쓰지 않는다. `Box<dyn Any>` 를 쓰지 않고, `serde_json::Value` 는 바깥(요청 본문, 모델 응답)을 받는 경계 한 곳에서만 쓰고 안쪽으로 넘기지 않는다. `dyn Any` 는 레포 검사가 실패로 잡는다.
9. 파일 크기는 규칙이 아니라 신호다. 600줄을 넘는 제품 파일은 레포 검사가 실패로 잡으므로, 넘기 전에 책임이 둘인지 보고 가른다.
10. `cargo clippy --all-targets -- -D warnings` 가 깨끗하다. `#[allow]` 는 이유를 같은 줄에 적을 때만.

## 설계 결정

- `main.rs` 는 설정을 읽어 `app.rs` 를 띄우는 것뿐이고, `app.rs` 가 라우터와 상태(trait 객체들)를 조립한다. 새 기능은 디렉터리 하나와 `app.rs` 의 한 줄이다.
- 환경 변수를 읽는 곳은 `shared/config.rs` 뿐이고, 거기서 읽는 이름은 모두 `.env.example` 에 있어야 한다. 같은 테스트가 본다. 이름은 TS API 와 같되 `APP_ENV` 만 예외다(ADR-0021). `APP_ENV`(`production` | `sandbox`)는 프로세스 환경에서만 오고, 그 값이 읽을 파일(`.env.production`, `.env.sandbox`)을 고른다. `NODE_ENV` 는 읽지 않는다.
- `DATABASE_URL` 이 없으면 기동하지 않는다. DB 를 쓰는 테스트도 없으면 이유를 적고 실패한다. 조용히 건너뛰지 않는다.
- 오류 본문은 Nest 모양 `{ statusCode, message, error }` 이고 `message` 는 문자열 또는 문자열 배열이다. 요청 검증 문구는 class-validator 의 것과 같다. 대화 웹이 `message` 만 읽으므로 이 모양을 바꾸지 않는다.
- 시각은 timestamptz ⇄ ISO-8601 밀리초 `Z` 다. 응답의 `Option` 은 JSON 에서 칸을 뺀다(TS 의 `undefined` 규칙).
- 위기 키워드 패턴과 고정 위기 문구는 `safety` 한 곳에만 둔다(ADR-0004). 감지 흐름을 약하게 만들지 않고, 바꿀 때는 감지 테스트를 먼저 쓴다.
- 로그와 오류 문구에 대화 본문, 리포트 본문, 사용자 식별 정보를 싣지 않는다(루트 `CLAUDE.md` "읽지 않는 것").
- 사용자 메시지는 답보다 먼저 저장하고, 답이 실패해도 지우지 않는다(턴은 `failed` 로 남는다). 과제·지원 수준·닫힘은 답이 끝난 턴에서만 바뀌고, 위기 턴만 받자마자 닫는다. 턴 id 는 클라이언트가 만든 멱등 키라 같은 세션의 같은 id 는 409 다(ADR-0028).
- 프롬프트는 역할(발화, 리포트, 위기 판정)마다 `x.y.z` 버전 상수를 갖는다(ADR-0022). 프롬프트 문구를 바꾸는 커밋이 같은 커밋에서 그 역할의 상수를 올린다. major 는 실측 기준선을 새로 잡는 변경, minor 는 같은 기준선에서 비교할 수 있는 문구 변경, patch 는 오탈자와 다듬기다.
- 모델 호출은 본문 없이 사실만 `llm_calls` 에 남기고, 비용과 집계는 뷰다. 모델 단가는 `model_prices` 테이블 한 곳에만 둔다. 코드에 단가표를 두지 않고, 모델을 더하면 마이그레이션으로 단가 행을 더한다(ADR-0022).
- `cargo` 는 `dev-tools/scripts/cargo.sh` 로 부른다. 이 머신의 PATH 에는 없다.
