# 위기 발화는 키워드와 모델 판정의 두 겹으로 보고, 어느 한쪽이라도 걸리면 고정 문구로 전문 자원에 넘기고 세션을 닫는다

## 맥락

자해나 자살을 말하는 사용자에게 일반 챗봇은 공감 발화를 이어 가다 신호를 놓치거나, 모델이 지어낸 연락처를 내밀 수 있다. 이 제품에서 그런 실수는 되돌릴 수 없다. 모바일 시기에는 위기 감지를 별도 모델(SafetyGuard, Gemini 2.5 Flash)에 맡겼고, 학술 가이드는 4단계 키워드표와 우선순위 1단계 "즉각적 안전"을 두었다. 웹 제품은 이것을 더 단순하고 재현 가능한 구조로 다시 만들었다.

## 결정

1. **발화를 만들기 전에 본다.** 모든 사용자 턴은 오케스트레이터의 첫 단계에서 위기 판정을 거친다. 판정이 위기면 단계 전이, 지식 검색, 발화 생성을 하지 않는다.
2. **두 겹, 합집합.** 결정론적 키워드 스크린이 먼저 보고, 걸리지 않으면 모델에게 YES/NO 로 묻는다. 어느 한쪽이라도 위기면 위기다. 안전은 오탐 쪽으로 기운다.
3. **키워드 패턴은 한 곳에만 둔다.** 도메인의 빠른 경로와 모델 실패 때의 폴백이 같은 패턴(`crisis-pattern.ts`)을 쓴다. 규칙이라서 회귀 실행이 재현된다. 지금 키워드는 영어뿐이고 다른 언어는 모델 판정이 맡는다.
4. **모델이 실패해도 키워드는 남는다.** 판정 호출이 실패하면 경고를 남기고 키워드 결과로 대신한다. 발화 생성의 실패는 오류로 올리지만 위기 판정만은 열화 대신 보수적인 폴백을 둔다.
5. **위기 답은 모델이 쓰지 않는다.** 고정 문구와 검증된 연락처만 보낸다. 지원 수준을 위기(3)로 올리고 세션을 닫는다. 지원 수준은 내려가지 않는다.
6. **위기 자원은 늘 무료이고 늘 보인다.** `GET /v1/safety/resources` 는 결제나 구독 뒤에 두지 않는다. 화면도 위기 자원을 숨기지 않는다.
7. **바꿀 때는 감지 테스트를 먼저 쓴다.** 이 흐름을 약하게 만드는 변경은 하지 않는다.

## 버린 것

| 안 | 이유 |
|---|---|
| 별도 안전 모델 하나에만 맡김(모바일 시기 SafetyGuard) | 모델 호출이 실패하거나 느릴 때 빈자리가 생긴다. 판정이 재현되지 않아 회귀 확인이 어렵다 |
| 키워드만 | 언어와 돌려 말하는 표현을 다 잡지 못한다. 키워드는 영어뿐이다 |
| 모델이 위기 답을 생성 | 연락처를 지어내거나 상황을 다룰 수 있다고 말할 위험이 있다(ADR-0003 의 위기 표현) |
| 위기 뒤에도 대화를 이어 감 | 지금은 넘기고 닫는다. 학술 가이드가 말한 24시간 뒤 후속 확인과 "돌아오고 싶을 때 돌아오라"는 마무리는 아직 하지 않았다 |
| 4단계 위험도를 모두 판정 | 코드에는 주의 수준(2, `SUPPORT_WATCH`)이 정의돼 있지만 판정은 1 아니면 3 만 낸다. 중간 단계의 행동이 정해지지 않았다 |

## 결과

- 오탐은 대화를 끊는다. 슬픔의 과장("나도 따라가고 싶다" 류)이 키워드에 걸리지 않도록 키워드는 관용 표현이 아닌 문구만 둔다. 모델 판정은 그런 문장을 위기로 볼 수 있고, 그 비용은 받아들인다.
- 위기 자원은 지금 한국 번호(109, 1577-1366)다. 대상 시장을 바꾸면 이 목록과 키워드 언어를 같이 바꾼다(ADR-0002). 번호는 배포 전에 다시 확인한다.
- 로드맵에 있던 "직전 대화 맥락을 위기 판정에 넣기"는 아직 하지 않았다. 지금은 한 메시지만 본다.
- LLM 을 바꾸면(ADR-0010) 위기 판정 프롬프트가 새 모델에서도 같은 답을 내는지 먼저 잰다. 판정이 YES 로 시작하는지 보는 방식은 모델의 출력 습관에 기댄다.
- 누가 잡았는지(`keyword`: 키워드가 걸림, `model`: 키워드는 안 걸리고 모델이 YES, `none`: 둘 다 아니거나 모델이 실패해 키워드 결과로 대신함)를 턴 분석 `risk_detected_by` 에 그대로 적는다(#21, 2026-10-21). 두 층의 효과를 계측(`crisis.model`)으로 보기 위한 것이고, 감지 규칙 자체는 바꾸지 않는다.
