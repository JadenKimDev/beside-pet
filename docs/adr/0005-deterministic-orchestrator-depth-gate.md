# 대화의 흐름은 코드가 정하고 모델은 단계 안의 발화만 쓴다. 단계는 애도의 네 과제이고, 깊이 게이트가 맴돌이를 막는다

## 맥락

모바일 시기의 상담 대화는 흐름을 프롬프트와 모델에 맡겼다. 5만 자가 넘는 상담 프롬프트, 세션 가이드 에이전트가 만든 할 일 목록, 분석 에이전트의 사후 판정이 겹쳐 있었고, 실측에서 같은 질문을 되묻거나 한 자리를 맴돌거나 너무 빨리 넘어가는 일이 반복됐다(DEV-2026-03-14-prompt-driven-session-structure, DEV-2026-03-15-session-guide-agent-pacing). 사용자는 "이 대화가 어디로 가는지 모르겠다"고 느끼고 떠난다. 공감하는 말이 모자란 것이 아니라 방향과 진행이 없었다.

## 결정

1. **명시적 오케스트레이터가 다음 할 일을 정한다.** 한 턴은 안전 확인, 단계 전이 판단, 지식 검색, 발화 생성, 턴 분석, 저장의 순서로 평범한 코드에서 돈다. 프레임워크의 그래프나 에이전트의 자율 판단을 쓰지 않는다.
2. **단계는 상태다.** 세션 애그리게이트의 `task`(0 온보딩, 1에서 4 Worden 의 애도 네 과제, 5 클로징)가 진행 위치이고, 진행률은 (task-1)/4 로 셈한다. 상태 전이는 애그리게이트의 메서드로만 일어나고, 닫힌 세션은 턴을 거부한다.
3. **깊이 게이트.** 전이 규칙은 순수 도메인 서비스가 전사에서 파생해 정한다. 한 단계에 최소 3턴(`MIN_DEPTH`) 머문 뒤 진솔한 답이 오면 넘어간다. "모르겠어요" 같은 비몰입이 2번(`DISENGAGE_EXIT`) 이어지면 부드럽게 일찍 넘어간다. 어떤 경우에도 5턴(`MAX_DEPTH`)이면 넘어간다. 카운터를 따로 저장하지 않는다.
4. **에이전트는 단계가 아니라 역할로 나눈다.** 세션 시작에 한 번 도는 Planner, 게이트를 통과할 때만 도는 Supervisor, 종료에 한 번 도는 Summarizer, 매 턴의 지식 검색 도구. 단계마다 에이전트를 만들지 않는다. 단계 정보는 발화 프롬프트에 매개변수로 넣는다.
5. **두 경로.** 온보딩에서 급성(최근 떠나보냄)과 예기(노령, 말기) 경로를 가르고, 모든 질문은 건너뛸 수 있다. 첫 단계는 진단이 아니라 "그 슬픔은 정당하다"는 인정이다.
6. **세션을 잇는다.** 새 대화는 온보딩을 다시 거치지 않고 직전 세션의 프로필을 이어받아 도달했던 단계에서 다시 시작하며, 직전 세션의 요약과 전사 꼬리를 재개 인사에 넣는다.

## 버린 것

| 안 | 이유 |
|---|---|
| 프롬프트 하나에 흐름 규칙을 모두 적기(모바일 시기) | 규칙이 길어질수록 모델이 일부를 놓쳤고, 모델을 바꾸면 흐름이 같이 바뀌었다 |
| 세션 가이드 에이전트가 할 일 목록을 만들어 매 턴 주입 | 진행을 다시 모델이 판단하게 된다. 호출이 늘고 디버깅이 어렵다 |
| 단계마다 전담 에이전트 | 역할이 겹치고 비대해진다 |
| 턴 수만으로 전이 | 몰입한 사용자를 너무 일찍 넘기고 비몰입 사용자를 붙잡는다. 게이트는 몰입 여부와 상한을 같이 본다 |

## 결과

- 전이 규칙이 읽히는 도메인 코드라 테스트와 교체가 쉽다. LLM 을 바꿔도(ADR-0010) 흐름은 바뀌지 않는다.
- 진행률이 숫자로 나오므로 화면에 진행 막대를 보여 주고, `turn_analyses` 로 단계 도달률을 SQL 로 셀 수 있다.
- 모델이 해석할 여지가 남는 곳은 "진솔한 답인가"의 판정과 발화 자체뿐이다. 여기서 품질이 갈린다.
- Rust 포팅은 이 상수(3, 2, 5)와 단계 번호, 진행률 계산을 그대로 옮긴다.
- 결정 6 의 재개 규칙(직전 세션의 기준, 7일과 위기 뒤의 과제 1, 매 턴에 들어가는 기억)은 ADR-0034 가 잇는다(2026-10-22).
