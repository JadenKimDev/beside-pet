# 사용자 턴은 받자마자 저장하고, 상태 전이는 끝난 턴에 속하며, 턴 id 는 클라이언트가 만든 멱등 키다

## 맥락

ADR-0018 은 한 턴을 안전 확인 → 과제 전이 → 지식 검색 → 발화 → 턴 분석 → 저장 순서로 두고, 모델 스트림이 도중에 실패하면 그 턴을 저장하지 않는다고 했다(TS 와 같다). 그 결과 모델 호출이 실패하거나 시간 제한을 넘기면 사용자가 보낸 말까지 사라지고, 턴이 도는 동안 화면을 떠났다 돌아오면 기록에 그 말이 없어 전송이 취소된 것처럼 보인다(#19). 또 클라이언트가 확인을 받지 못한 전송을 다시 보내면 같은 말이 두 번 저장된다.

## 결정

1. **턴은 사실이다.** 새 테이블 `turns`(id, 세션, 상태 `pending`·`done`·`failed`, 시작과 끝 시각, 오류 종류)를 두고 `messages` 가 `turn_id` 로 가리킨다. 첫 인사도 턴 하나다. 본문은 지금처럼 `messages.text` 뿐이고, 턴 행에는 일어난 일(받았다, 끝났다, 실패했다와 그 종류)만 적는다.
2. **사용자 턴은 받자마자 저장한다.** 순서는 안전 확인 → 사용자 메시지와 `pending` 턴을 한 트랜잭션으로 저장 → `meta` → 지식 검색 → 발화 → 답과 턴 분석과 `done` 턴 저장이다. `meta` 는 저장 뒤에 나가므로 클라이언트는 `meta` 를 "서버가 받았다"는 확인으로 쓴다. 발화 모델이 실패하거나 시간 제한을 넘기면 턴을 `failed` 로, 종류를 적어 저장한다. 사용자 메시지는 남는다. 서버가 기동할 때 `pending` 으로 남은 턴은 `failed`(`restart`)로 닫는다. ADR-0018 결과의 "모델 스트림이 도중에 실패하면 그 턴은 저장하지 않는다"를 이 결정이 대신한다.
3. **상태 전이는 답이 끝난 턴에 속한다.** 과제 전이, 지원 수준, 닫힘은 두 번째 저장에서만 바뀐다. 첫 저장은 세션 상태를 바꾸지 않고 메시지와 턴만 더한다. 실패한 턴은 상태를 움직이지 않으므로 같은 메시지로 다시 받을 때 같은 전이가 나온다(깊이 게이트는 결정론, ADR-0005). 세션 애그리게이트는 "메시지 받기"와 "전이 계산·적용"을 따로 가진다. 위기 턴은 예외다. 키워드 ∪ 모델 판정이 위기면 받자마자 닫고 고정 문구를 적으며 턴은 바로 `done` 이다(ADR-0004 의 감지 흐름을 약하게 만들지 않는다).
4. **턴 id 는 클라이언트가 만든 멱등 키다.** `POST /v1/sessions/{id}/messages` 와 `/messages/stream` 의 본문에 `turnId`(UUID, 선택)를 더한다. 같은 세션에 같은 `turnId` 가 다시 오면 새 턴을 만들지 않고 `409 { message: "Turn already received" }` 다. 없으면 서버가 만든다(옛 호출과 chat-eval 도구가 그대로 돈다). `GET /v1/sessions/{id}/messages` 의 항목에 `turnId` 를 더한다. 엔드포인트의 겉에 칸을 더하는 것이므로 웹과 함께 한 PRD 로 다룬다(ADR-0015).
5. **웹은 확인을 기다리고 한 번만 다시 보낸다.** 보낸 메시지를 "보내는 중"으로 두고 `meta` 에서 지운다. `meta` 전에 끊기면 같은 `turnId` 로 한 번 자동으로 다시 보내고, 409 를 받으면 기록을 다시 읽는다. `meta` 뒤에 끊기면 사용자 메시지는 두고 빈 답 말풍선만 지운다. 대화 흐름의 판단은 서버에 둔다.

## 버린 것

| 안 | 이유 |
|---|---|
| 지금처럼 턴 끝에 한 번 저장하고 웹이 실패한 말을 다시 보내게 둠 | 서버가 받았는지 클라이언트가 알 수 없어 같은 말이 두 번 저장되거나 사라진다. "받았다"는 사실이 DB 에 없다 |
| 멱등 키를 서버가 만들어 응답으로 돌려줌 | 응답을 받기 전에 끊긴 전송이 바로 문제이므로 키는 요청에 실려야 한다 |
| 첫 저장에서 과제 전이까지 적용 | 답이 실패한 턴이 상태를 움직여, 같은 말을 다시 받으면 전이가 두 번 일어난다. 전이는 답이 끝난 턴의 것이다 |
| 사용자 메시지에 상태 칸(`pending`)을 둠 | 턴과 메시지는 다른 사실이다. 첫 인사 턴에는 사용자 메시지가 없고, 실패의 종류는 메시지가 아니라 턴의 것이다 |
| 턴 재접속과 중단을 함께 함 | 진행 중인 답에 다시 붙는 것은 스트림을 서버에 두는 다른 설계가 필요하다. 다음 PRD 로 미룬다 |

## 결과

- 모델이 실패해도 사용자의 말은 기록에 남고, 턴의 `failed` 행과 종류로 왜 답이 없는지 셀 수 있다.
- 세션 상태는 `done` 턴에서만 움직이므로 실패한 턴을 다시 받아도 전이가 중복되지 않는다.
- 요청 본문과 기록 응답에 `turnId` 칸이 늘었다. 그 밖의 겉(경로, 이벤트, 오류 모양)은 그대로다.
- `apps/server/CLAUDE.md` 설계 결정에 "사용자 메시지는 답보다 먼저 저장하고 실패해도 지우지 않는다. 과제·지원 수준·닫힘은 답이 끝난 턴에서만 바뀐다(위기 제외)"를 둔다.
