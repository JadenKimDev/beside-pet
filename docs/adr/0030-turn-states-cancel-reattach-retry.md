# 답이 흐르는 턴은 서버 메모리의 등록부로 다시 붙고 중단하며, 중단한 턴은 저장하되 숨기고, 실패한 턴은 사용자가 답만 다시 받는다

## 맥락

ADR-0028 로 사용자 턴은 받자마자 `pending` 으로 저장되고 답이 끝나면 `done`, 실패하면 `failed` 가 됐다. 그래도 답 쪽에는 길이 없었다. 답이 흐르는 동안 화면을 떠나면 다시 붙을 수 없고, 답이 실패하면 말을 다시 보내는 것 말고는 길이 없으며, 흐르는 답을 멈출 수도 없다(#20). 서버가 다시 뜨면 진행 중이던 턴은 기동 정리가 `failed`(`restart`)로 닫는다(ADR-0028).

사용자는 2026-10-20 에 "중단한 턴은 저장하되 사용자에게는 보이지 않는다"로 정했다. 일어난 일은 남기되(루트 `CLAUDE.md` "데이터를 두는 원칙") 사용자의 화면과 대화의 맥락에서는 없는 것으로 다룬다는 뜻이다.

## 결정

1. **턴 상태를 넷에서 다섯으로.** `turns.status` 에 `streaming`(답이 흐르는 중)과 `cancelled` 를 더한다. `pending` 은 메시지는 받았으나 답이 시작하지 않은 상태로 좁아진다. 전이는 `pending → streaming → done | failed | cancelled` 이고, `pending` 에서 바로 `cancelled` 도 된다.
2. **중단한 턴은 저장하되 숨긴다.** 중단하면 사용자 메시지와 거기까지 온 부분 답을 `messages` 에 그 턴 id 로 저장하고 턴을 `cancelled` 로 적는다. 턴 분석은 쓰지 않고 세션 상태(과제, 지원 수준, 닫힘)도 바꾸지 않는다(전이는 끝난 턴에 속한다, ADR-0028). `cancelled` 턴의 메시지는 기록 응답(`GET /v1/sessions/{id}/messages`)과 세션의 `history()`(발화 프롬프트의 대화 창, 깊이 게이트의 답 목록, 세션 잇기의 전사 꼬리)에서 빠진다. 행은 지우지 않으므로 스냅샷 저장(꼬리 삭제 upsert, ADR-0018)은 숨은 행까지 들고 `history()` 만 거른다. 세션 삭제의 연쇄(ADR-0006)는 숨은 행도 지운다.
3. **다시 붙기는 서버 메모리의 등록부로.** 진행 중 턴 등록부(`support/flow/active.rs`)가 턴 id 마다 지금까지 모은 답 글, 구독자 채널, 중단 토큰을 든다. 발화가 시작할 때 등록하고 끝나면 뺀다. 새로 붙는 스트림은 모은 글을 `token` 하나로 먼저 받고 이어지는 조각을 받는다. 등록부는 프로세스 하나의 메모리에만 있고 DB 에 두지 않는다. 서버가 다시 뜨면 비어 있고, 그때 남은 `pending`·`streaming` 턴은 기동 정리가 `failed`(`restart`)로 닫는다.
4. **중단은 토큰으로, 공급자 코드는 그대로.** 모델 호출을 감싸는 흐름(`flow/deadline.rs`)이 중단 토큰을 함께 보고, 중단되면 모델 스트림을 더 읽지 않고 버린다(공급자 연결이 닫힌다). 공급자(`llm/provider`)는 고치지 않는다. 끊은 호출은 `llm_calls` 에 결과 `cancelled` 로 남는다(ADR-0022 의 기록 원칙, 세부는 #22).
5. **실패한 턴은 사용자가 답만 다시 받는다.** `POST …/turns/{turnId}/retry` 가 같은 사용자 메시지로 같은 전이를 다시 계산해 `pending → streaming → done` 을 밟는다. 사용자 행은 하나뿐이다. 자동 재시도는 두지 않는다. 로컬 모델의 시간 제한(120초, ADR-0018)이 있어 서버가 혼자 다시 돌면 기다림이 두 배가 된다. 실패는 바로 보여 주고 사용자가 정한다.
6. **위기 턴과 첫 인사는 중단 대상이 아니다.** 위기 턴은 고정 문구가 바로 나가고 `done` 이 되므로 등록부에 들어가지 않는다(ADR-0004 의 흐름을 약하게 만들지 않는다). 첫 인사(시작 턴)는 사용자 메시지가 없어 중단할 것이 없다.
7. **겉은 웹과 함께 넓힌다(ADR-0015).** 새 엔드포인트 셋(`GET …/turns/{turnId}/stream`, `POST …/turns/{turnId}/cancel`, `POST …/turns/{turnId}/retry`)과 세션 상태 응답의 `activeTurn`·`failedTurn`, 새 SSE 이벤트 `cancelled` 는 이 PRD 가 웹과 서버를 같이 고친다.

## 버린 것

| 대안 | 버린 이유 |
|---|---|
| 중단한 턴을 지운다 | 일어난 일을 지우는 것이고, 사용자가 "저장하되 보이지 않게"로 정했다. 행이 남아야 계측(#22 의 `cancelled`)이 가능하다 |
| 등록부를 DB 에 둔다 | 조각 단위의 쓰기가 많고, 서버 하나뿐이라 프로세스 메모리로 충분하다. 재시작은 `failed(restart)` 로 닫으면 된다 |
| 서버의 자동 재시도 | 시간 제한이 긴 로컬 모델에서 기다림이 두 배가 된다. 사용자의 선택으로 둔다 |
| 중단을 공급자 안에서 처리 | 공급자마다 코드가 생긴다. 흐름이 토큰 하나로 감싸면 공급자는 그대로다 |
| 숨은 턴을 프롬프트에는 넣기 | 사용자가 없던 일로 하겠다고 중단한 말이 다음 답에 영향을 주면 안 된다 |

## 결과

- 실패한 턴의 사용자 말은 `history()` 에 남지만 답이 없는 채로 다음 발화 프롬프트에 들어간다(#19 가 남긴 문제). 이 PRD 는 실패한 턴의 사용자 말을 다음 턴의 프롬프트 대화 창에서는 빼고 깊이 계산에서도 빼되, 기록 응답에는 "답 다시 받기"와 함께 보인다. 사용자가 다시 받거나 새 말을 보내면 그 턴은 그대로 `failed` 로 남는다.
- 같은 `turnId` 가 동시에 두 번 오는 경합은 저장의 upsert 가 같은 세션은 받으므로 둘째 요청이 `409 Turn already received` 를 받지 못할 수 있다. 이 PRD 는 등록부에 턴 id 를 먼저 올리는 것으로 같은 프로세스 안의 경합을 막는다.
- 웹은 `activeTurn` 이 있으면 흐르는 말풍선을 두고 turn stream 에 붙고, `failedTurn` 이 있으면 "답 다시 받기"를 둔다. 중단하면 두 말풍선을 빼고 사용자 글을 입력창에 되돌린다.
- `apps/server/CLAUDE.md` 설계 결정에 "중단한 턴의 메시지는 지우지 않고 숨긴다" 한 줄을 둔다.
