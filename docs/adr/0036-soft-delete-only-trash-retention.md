# 삭제는 소프트 삭제만이다. 지운 대화와 리포트는 3개월 보관함에 두고 되살릴 수 있으며, 행을 지우는 것은 기동 때의 파기뿐이다. 계정은 삭제(soft delete) 3개월 뒤에만 대화·기억까지 연쇄로 지운다

## 맥락

ADR-0006 은 "대화를 지우면 전사와 리포트와 턴 분석을 한 트랜잭션으로 지운다"고 정했고, ADR-0034 가 그 연쇄에 기억 행을 더했다. 그래서 사용자가 더보기 메뉴에서 한 번 잘못 누르면 대화와 거기서 나온 기억이 바로 사라졌다. 리포트는 세션 행의 `report` 칸이라 대화를 두고 따로 지울 길이 없었다. 관리자의 계정 완전 삭제는 `accounts` 행만 지워 그 사람의 대화와 기억이 주인 없이 남았다(ADR-0006 "비어 있는 곳"). 대화 원문의 보존 기간도 정해지지 않은 채였다.

이 제품의 사용자는 슬픔의 한가운데에 있는 사람이다. 지우고 싶은 날과 다시 보고 싶은 날이 다를 수 있다. 2026-10-22 사용자가 정했다: 하드 삭제는 사용자와 관리자의 조작으로 일어나지 않는다.

## 결정

- **사용자와 관리자의 조작은 시각만 적는다.** `sessions.deleted_at`, `sessions.report_deleted_at`, `accounts.deleted_at`(timestamptz, NULL 이 "살아 있음"). 행, 메시지, 턴 분석, 기억 행은 그대로 둔다. 보관 만료는 저장하지 않고 쿼리로 계산한다(루트 `CLAUDE.md` "데이터를 두는 원칙").
- **보존 기간은 3개월 하나다.** 세션·리포트·계정 공통의 코드 상수 `TRASH_RETENTION_MONTHS = 3` 이고, 기억의 12개월 파기 상수와 같은 자리(`support/store` 의 파기 모듈)에 둔다. 환경 변수로 두지 않는다. 운영 설정이 아니라 사용자에게 한 약속이기 때문이다.
- **지운 대화는 없는 대화다.** 세션 하나를 찾는 모든 경로가 지운 세션을 404 로 본다. 예외는 되살리기와 보관함 목록뿐이다. 목록, 온보딩 분기, 재개의 직전 세션, 기억 블록이 모두 살아 있는 세션만 본다. 뷰 `current_memory` 는 출처 세션이 살아 있는 행만 내므로, 되살리면 기억도 손대지 않고 함께 돌아온다.
- **리포트는 대화와 따로 지우고 되살린다.** `report_deleted_at` 만 적고 `report` 칸은 남긴다. 지운 리포트의 `GET …/report` 는 404 이고 다시 만들지 않는다(ADR-0008, 한 번만 쓴다). 되살리면 같은 본문이 돌아온다.
- **행을 지우는 것은 기동 때의 파기뿐이다.** 서버가 뜰 때 한 번, 리포트(3개월 지난 `report_deleted_at` 의 `report` 칸 비우기) → 세션(3개월 지난 `deleted_at` 의 연쇄 삭제, ADR-0006·ADR-0034 의 경로 그대로) → 계정(상태 `Deleted` 이고 `deleted_at` 이 3개월 지난 계정의 세션 연쇄와 `accounts` 행) → 기억 12개월(기존) 순으로 돈다. 로그에는 행 수만 남긴다.
- **관리자의 완전 삭제는 삭제(soft delete) 3개월 뒤에만 된다.** 운영 화면의 "삭제"(`soft_delete`, 상태 `Deleted`, ADR-0017)가 `deleted_at` 을 적고 "복구"가 비운다. 로그인만 막는 "정지"(`revoke`, 상태 `Revoked`)는 이 시계와 무관하다. 3개월 전의 완전 삭제는 409 `Account must be suspended for 3 months before deletion` 이다. 통과하면 그 사람의 세션·메시지·턴·분석·기억·계정 행을 한 트랜잭션으로 지운다. ADR-0006 의 "비어 있는 곳"은 이것으로 메운다.
- **엔드포인트의 겉은 그대로다(ADR-0015).** 기존 `DELETE /v1/sessions/{id}` 는 뜻만 소프트 삭제로 바뀌고 멱등 204 다. 더한 것은 `GET /v1/sessions/deleted`, `POST …/restore`, `DELETE …/report`, `POST …/report/restore` 와 응답 칸 `reportDeleted`, `deletedAt`, `purgeAt` 뿐이다.

## 버린 것

| 안 | 이유 |
|---|---|
| 즉시 하드 삭제 유지(ADR-0006) | 잘못 누른 한 번이 되돌릴 수 없다. 잊혀질 권리는 3개월 뒤의 파기로 똑같이 지킨다 |
| 리포트를 지우면 `report` 칸을 바로 비움 | 되살릴 수 없고, 다시 만들 수도 없다(ADR-0008). 시각만 적고 칸은 둔다 |
| 보관 만료 시각(`purge_at`)을 칸으로 저장 | `deleted_at + 3개월`로 계산되는 값이다. 응답의 `purgeAt` 은 서버가 셈해 줄 뿐이다 |
| 보존 기간을 환경 변수로 | 환경마다 다를 이유가 없고, 사용자에게 보이는 문구("3개월")와 어긋날 수 있다 |
| 파기를 주기 작업(cron)으로 | 서버 한 대라 기동 때 한 번으로 충분하다. 기억 파기와 같은 자리에 두어 순서를 한 곳에서 본다 |
| 본인 탈퇴 엔드포인트 | 아직 없다. 지금은 관리자의 정지와 완전 삭제만 있고, 본인 탈퇴는 다음 결정이다 |
| 계정 완전 삭제를 정지와 무관하게 허용 | 3개월의 유예가 계정에도 똑같이 있어야 대화의 유예가 뜻이 있다. 정지 뒤 3개월만 허용한다 |

## 결과

- ADR-0006 의 "대화 삭제는 연쇄다"와 "계정 삭제의 연쇄는 아직 없다"는 이 글이 대신한다. 본인만 읽는다, 모델 키와 본문은 서버에만, 개발 데이터는 지어낸 값, 학습에 쓰지 않는다는 선은 그대로다.
- 지운 세션의 본문은 3개월 동안 DB 에 남는다. "읽지 않는 것"의 선은 같다. sandbox 복사본의 자리 표시자 치환(`sandbox-scrub.sql`)도 지운 행에 똑같이 적용된다.
- 마이그레이션은 칸 셋을 더하고 뷰를 바꿀 뿐이다. 기존 행의 뜻은 바뀌지 않고, 새 조건 아래서 기존 사용자 데이터가 새로 지워지는 일은 없다.
- 본인 탈퇴(사용자가 스스로 계정을 정지하는 길)와 지운 대화의 다운로드는 정하지 않았다. 정하면 새 ADR 을 쓴다.
