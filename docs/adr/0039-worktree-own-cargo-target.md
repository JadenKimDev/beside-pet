# 워크트리는 자기 `target/` 을 쓴다 (ADR-0037 의 결정 1 을 뒤집는다)

## 맥락

ADR-0037 은 디스크를 아끼려고 워크트리가 본 체크아웃의 `target/` 하나를 같이 쓰게 했다. 그 근거는 "cargo 가 잠금으로 동시 빌드를 직렬화하므로 안전하다" 와 "우리 크레이트만 경로가 해시에 들어가 워크트리마다 따로 컴파일된다" 였다.

#49 에서 S1 의 red 기록이 남의 바이너리로 찍혔고, S4 의 verify 가 한 번 실패했으며, QA 가 옛 바이너리의 서버를 띄웠다. 2026-10-23 에 재 보니(`docs/research/2026-10-23-공유-target-충돌-실측.md`, 모두 등급 A) 두 근거가 모두 틀렸다.

- cargo 의 산출물 이름 해시(metadata)에 워크스페이스 크레이트의 절대 경로가 들어가지 않는다. 두 체크아웃이 같은 이름의 파일(`beside_pet_server-<해시>`, `purge-…`, `routes-…`, `schema-…`, `target/debug/beside-pet-server`)을 쓰고, 마지막에 컴파일한 쪽이 덮는다. 워크트리의 `build --tests` 뒤 여섯 파일의 sha 가 모두 바뀌었다.
- 지문(fingerprint)은 자기 소스의 mtime 과 내용만 본다. 덮인 쪽에서 다시 빌드해도 자기 소스가 바뀌지 않았으면 Compiling 0 으로 끝나고 남의 바이너리를 그대로 쓴다. 그 테스트 바이너리의 `--list` 에 상대 워크트리에만 있는 테스트가 나왔다.
- 동시에 돌리면 잠금은 걸리지만(`Blocking waiting for file lock`), 기다린 쪽은 Compiling 0 으로 끝나며 상대가 만든 바이너리를 `Executable` 로 정상 출력한다(3회 중 2회). 나머지 1회는 둘이 동시에 4G 비우기에 들어가 한쪽이 `IO error … target/tmp` 로 실패했다.
- 같은 `lib.rs` 수정의 재빌드가 공유 `target/` 에서 번갈아 할 때 약 10초, 따로 된 `target/` 에서 약 1.8초였다. 번갈아 빌드하면 `target/` 이 한 번에 약 0.3G 씩 커져 6~7회마다 4G 비우기(23~27초, 226개 재컴파일)가 들어갔다.

러너(ADR-0032)의 판정도 같은 `target/` 을 지나므로 같은 오염에 노출된다. 판정의 정본이 남의 바이너리로 찍힐 수 있다는 뜻이다.

## 결정

1. **워크트리는 cargo 기본대로 자기 `target/` 을 쓴다.** `dev-tools/scripts/cargo.sh` 에서 "워크트리면 본 체크아웃의 `target/` 을 쓴다" 블록을 지운다. 환경의 `CARGO_TARGET_DIR` 은 지금처럼 따른다. ADR-0037 의 결정 1 은 이 ADR 이 대신한다.
2. **ADR-0037 의 결정 2(4G 를 넘으면 `cargo.sh` 가 비운다)는 그대로 둔다.** 다만 비우는 대상이 자기 `target/` 이 되므로 두 체크아웃이 같은 순간 비우기에 들어가는 일은 없다.
3. 워크트리의 `target/` 은 워크트리와 함께 사라진다(`pnpm wt:remove` 가 디렉터리를 지운다). 따로 치울 것은 없다.

## 버린 것

- **공유를 유지하고 크레이트 이름을 워크트리마다 다르게 두기.** 산출물 이름이 갈려 덮어쓰기는 피하지만, `Cargo.toml` 이 체크아웃마다 달라져 커밋할 수 없고, `beside-pet-server` 라는 이름에 기댄 명령과 문서가 모두 조건부가 된다.
- **sccache.** 컴파일 결과를 캐시해 따로 된 `target/` 의 첫 빌드를 줄일 수는 있지만, 문제의 본질(같은 이름의 최종 바이너리를 두 트리가 번갈아 쓴다)은 그대로다. 첫 빌드 23초를 줄이려고 도구 하나를 더 들일 만큼 비용이 크지 않다.
- **`--artifact-dir` 로 최종 바이너리만 따로 두기.** nightly 전용이다. deps 의 테스트 바이너리와 지문은 여전히 공유되어 Compiling 0 문제가 남는다.

## 결과

- 바뀌는 것: 워크트리마다 첫 빌드 약 23초와 1.9G(`build --tests`, 2026-10-23, 이 머신). 워크트리를 셋 띄우면 `target/` 이 최대 네 벌이다.
- 얻는 것: 워크트리끼리, 그리고 러너와 사람 사이에 바이너리가 섞이지 않는다. 번갈아 고칠 때의 재빌드가 약 10초에서 약 1.8초로 준다. 같은 순간 비우기가 겹쳐 실패하는 일이 없다.
- 본 체크아웃의 `pnpm test` 와 4G 비우기는 전과 같다.

## 근거

- 실측 보고서: `docs/research/2026-10-23-공유-target-충돌-실측.md`(로컬). 재현 스크립트 `outputs/measure-target-collision/run.sh`.
- 재현: 워크트리 둘 중 한쪽의 테스트 파일에 `#[test] fn marker() {}` 를 더하고 `cargo.sh build -p beside-pet-server --tests` 를 돌린 뒤, 다른 쪽에서 같은 명령을 돌린다. 공유 `target/` 에서는 Compiling 0 이고 남은 테스트 바이너리의 `--list` 에 `marker` 가 있다.
- 이슈 #49(오염을 처음 본 자리), #53(이 결정).
