# 프롬프트를 70% 줄였더니 빨라졌지만, 금지 표현과 질문 없음은 그대로였다

## 맥락

모바일 시기의 상담 모델은 Gemini 2.5 Flash(`thinkingBudget: 0`)였다. 시스템 프롬프트가 XML 999줄이었고, 응답에 "It sounds like" 같은 진부한 위로 문구가 반복되며 개방형 질문을 하지 않았다. 프롬프트가 길고 복잡해서 모델이 규칙을 놓친다고 보고 다시 썼다.

## 해 본 것

1. XML 999줄을 Markdown 약 300줄로 줄였다. 규칙보다 앞에 BAD/GOOD 예시 7쌍을 두고, 대안이 붙은 금지 표현 목록과 self-check 절을 넣었다.
2. 맥락(반려동물 정보, 세션 상태)을 시스템 프롬프트에서 빼 사용자 메시지 앞에 붙였다.
3. 캐시 키에서 `tokenBudget` 을 빼고 언어만 남겼다.
4. 같은 시나리오(안락사 뒤의 13턴 대화)로 전후를 비교했다.

## 결과

- 좋아진 것: 평균 단어 수 약 75에서 약 49, 전체 응답 5.3초에서 3.3초, 첫 텍스트 2.9초에서 2.0초, TTFB 191ms 에서 144ms. 캐시 적중이 거의 0에서 거의 100%가 됐다(3의 효과).
- 그대로인 것: 금지 표현이 13턴 중 11턴에 나왔고(모두 24회, "It sounds like" 만 11회), 개방형 질문은 13턴 중 0회였다.
- 보고서는 근본 원인을 `thinkingBudget: 0` 으로 보았다. 생각 단계 없이 바로 토큰을 내는 모델은 규칙 문장과 self-check 를 실행하지 않는다는 것이다. frequency penalty 를 0.4에서 0.6으로 올리면 이번에는 같은 말을 되받는 "앵무새" 반복이 생겼다.
- 교훈: 프롬프트 다이어트는 속도와 비용에는 듣지만 행동 규칙의 준수를 사지 못한다. 규칙을 지키게 하려면 모델에 맞는 예시 중심 프롬프트를 따로 쓰거나(DEV-2026-03-16-model-specific-prompts, 같은 Flash 가 전용 프롬프트로 질문을 했다), 지켜야 하는 것을 코드로 옮긴다(ADR-0005). 이 진단("생각 단계가 없으면 질문하지 않는다")은 3월 16일 실측과 어긋나므로 절대 법칙으로 읽지 않는다.
- 캐시 키에 매 요청 바뀌는 값을 넣으면 캐시가 통째로 무력해진다. 모델 교체 때 다시 확인할 것.
