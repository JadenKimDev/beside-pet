# 문서와 코드를 전수 비교했더니 19건이 어긋났고, 그중 하나는 개인정보 고지의 누락이었다

## 맥락

모바일 시기 3주 동안 v2 문서(사업, 설계, 개발, 법률)를 많이 썼고 코드도 빠르게 바뀌었다. 새로 일을 시작하는 사람이 어느 쪽을 믿어야 하는지 알 수 없었다. 2026-03-13 에 v2 문서와 규칙 파일을 백엔드, 프론트엔드 코드와 하나씩 맞대었다.

## 해 본 것

1. 문서마다 주장하는 사실(인증, 모듈, 경로, 모델, 가격, 기능 상태)을 뽑아 코드와 비교했다.
2. 어긋남을 Critical(코드와 명백히 다름), Major(누락이나 구조 불일치), Minor 로 나눴다.

## 결과

- Critical 5건, Major 8건, Minor 6건, 모두 19건.
- 대표 사례: 인증 문서는 Supabase Auth 인데 코드는 Firebase Auth 였다. 문서에는 별도 온보딩 모듈과 7개 엔드포인트가 있었지만 코드는 엔드포인트 하나였다. 모듈 11개 중 5개(구독, 면책, 기분, 신고, 관리자)가 API 문서에 없었다. Swagger 경로가 틀렸다. 가격 문서 하나는 Basic $6.99, 시드는 $7.99 였다. 쓰지 않는 의존성(go_router)이 남아 있었다.
- 가장 무거운 것은 C-5 였다. 개인정보 가이드의 데이터 흐름에 실제 기본 상담 모델의 제공자(OpenAI)가 빠져 있었다. 개인정보 처리자를 고지하지 않은 셈이라 법적 문제로 이어질 수 있었다(ADR-0012).
- 원인은 하나였다. 결정이 바뀔 때 결정만 따로 적는 곳이 없어서, 같은 사실이 여러 문서에 흩어져 있었고 그중 일부만 고쳐졌다. 가격은 다섯 문서에 다른 값으로 남았다(ADR-0013).
- 교훈: 같은 사실은 한 곳에만 둔다. 코드가 정본인 사실(엔드포인트, 칸, 모델 이름)은 문서에 복사하지 않고 코드를 가리킨다. 결정이 바뀌면 옛 글을 고치지 않고 새 ADR 로 대신한다. 이 레포의 ADR 형식과 `CLAUDE.md` 의 "같은 사실은 한 곳에만" 규칙이 막으려는 것이 바로 이 일이다.
- 이번 이식에서도 같은 종류의 어긋남이 남아 있었다. 포트폴리오 사례는 "탈퇴하면 연쇄 삭제"라고 했지만 코드는 그렇지 않다(ADR-0006). RAG README 의 pgvector 적재는 코드에 없다(ADR-0014).
