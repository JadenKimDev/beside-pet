# 모바일 앱을 MVP 85에서 90%에서 멈췄다. 남은 일은 기능이 아니라 출시의 벽이었다

## 맥락

2026-03-26 Flutter 앱과 그 API 의 개발을 멈췄다. 중단 문서는 중단의 이유를 적지 않았다. 적어 둔 것은 그때의 상태, 내린 자원, 다시 시작할 순서다. 아래 "결과"의 해석 중 이유에 관한 것은 남은 일의 목록에서 읽어 낸 추정이다.

## 해 본 것

1. 비용이 나가는 자원을 내렸다. Cloud Run dev 서비스와 Artifact Registry(서울 리전 6.2GB, us-central1)를 지우고 Cloud Build 트리거를 껐다. Secret Manager(월 약 0.36달러)와 Firebase 무료 티어는 남겼다. 운영 GCP 프로젝트는 설정 파일에만 있었고 만든 적이 없었다.
2. 다시 시작할 절차(저장소 재생성, 트리거 재활성화, 로컬 실행)를 명령째 적었다.
3. 완성된 것과 남은 것을 적었다. 백엔드 모듈 11개와 엔드포인트 73개 이상, DB 테이블 27개, 에이전트 6개, 앱 기능 6개와 탭 5개는 완성. 남은 것은 BUG-001(다음 주제 미전달), PDF 생성을 앱으로 옮기기, 테스트 커버리지(백엔드 테스트 파일 0개), 미국 리전 운영 인프라, 앱스토어 제출, 약관의 미국 변호사 검토, 접근성 검증.

## 결과

- 기능은 거의 다 있었지만 출시까지의 벽(결제 실연동, 스토어 심사, 미국 리전 운영, 법률 검토, 테스트 0%)은 그대로였다. 혼자서 넘기 어려운 쪽이 남아 있었다(추정).
- 마지막 2주의 작업은 대부분 프롬프트 튜닝과 모델 비교였고, 결론이 며칠마다 바뀌었다(DEV-2026-03-15-session-guide-agent-pacing, ADR-0011). 대화 품질이 프롬프트에 묶여 있는 한 끝나지 않는 일이었다.
- 중단 문서가 "기억해야 할 설계 결정"으로 남긴 것 가운데 워딩 정책(ADR-0003)은 지금도 살아 있고, 미국 시장(ADR-0001)과 에이전트 역할 분리(ADR-0011)는 효력을 잃었다.
- 그 뒤 웹 제품을 새로 만들어 AWS 에 올렸다가, 2026-10-16 모바일 앱을 접고 웹만 남기기로 했다(ADR-0009). 같은 날 AWS 자원을 모두 내렸다. 두 번의 중단 모두 "다시 올릴 때 손으로 만든 자원을 기억으로 되살려야 한다"는 문제를 남겼다. 이번에는 `infra/` 코드로 만든다.
- 교훈: 중단 문서에는 상태와 절차뿐 아니라 이유를 한 줄 적는다. 다음에 재개를 판단할 때 가장 필요한 것이 그것이다. 테스트 0%로 기능을 쌓으면 재개 비용이 커진다.
